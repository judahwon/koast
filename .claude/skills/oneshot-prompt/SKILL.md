# oneshot-prompt

주제 한 줄을 받아 **`/loop` + `ultracode`에 그대로 붙여 넣을 원샷 프롬프트**를 생성한다.

산출물은 프롬프트 텍스트 파일 하나다. 이 스킬은 프로그램을 만들지 않는다.

## 왜 필요한가

철학을 이해하는 것과, 매번 그 철학을 빠짐없이 프롬프트에 녹여 쓰는 것은 다른 일이다.
사람은 반드시 빠뜨린다. 이 스킬이 대신 채운다.

`"예쁘게 만들어 줘"`와 `"영국 ○○ 앱보다 낫게, 아래 7개 항목 전부 Yes가 될 때까지"`의
차이가 결과물의 차이다.

## 절대 규칙

1. **기준점 없이 프롬프트를 뱉지 않는다.** 비교 대상이 없으면 리서치해서 만들어 낸다.
   그래도 없으면 사용자에게 묻는다. "좋게"·"예쁘게"·"고품질"은 목표가 아니다.
2. **리서치를 건너뛰지 않는다.** 기준점의 구체적 사실(스펙·수치·특징)이 프롬프트 안에
   들어가야 한다. "○○처럼"만 쓰면 받는 모델이 자기 상상으로 채운다.
3. **공유 상태를 만지는 작업은 팬아웃하지 않는다.** (아래 3단계 참조)
4. **생성자와 검증자를 분리한다.** 프롬프트에 "자기가 만든 걸 자기가 채점하지 마"를
   명시적으로 넣는다.
5. **종료 조건은 검증자가 쥔다.** "완벽할 때까지"가 아니라 "체크리스트 전항 Yes + 최대 N라운드".

## 절차

### 0단계 — 입력 파싱

인자에서 만들 대상을 읽는다. 불명확하면 **최대 2개**만 묻는다. 이건 인터뷰 스킬이 아니다.

물어도 되는 것: 산출물 형태(웹/앱/CLI), 기술 스택 제약, 비교 대상 선호.
묻지 말 것: 리서치로 알아낼 수 있는 모든 것.

### 1단계 — 리서치 선행 (생략 금지)

WebSearch로 해당 분야 **최상위 결과물**을 조사한다. 최소 3개 후보를 찾는다.

수집 대상:
- 그 분야에서 최고로 인정받는 제품·앱·사이트·게임 이름
- **구체적 사실**: 화면 구성, 핵심 인터랙션, 수치 스펙, 상징적 특징
- 사용자가 좋다고 말하는 이유 (리뷰·기사·비교글)
- 재현 대상이 특정 작품이면: 공개 스펙, 스크린샷, 영상 자료의 존재 여부

> 재현이 아니라 신규 제작이어도 참조 대상은 반드시 존재한다.
> "이 분야에서 가장 잘 만든 것"을 찾으면 그게 기준점이다.

### 2단계 — 외부 기준점 고정

리서치 결과에서 **비교 대상 1~2개**를 고른다. 선정 이유를 한 줄로 적는다.

기준점은 프롬프트 **맨 앞**에 배치한다. 목표를 먼저 못 박아야 이후 모든 판단이 그쪽을 향한다.

### 3단계 — 작업 분해: 팬아웃 vs 순차

전체를 항목으로 쪼갠 뒤, 각 항목을 두 통 중 하나에 넣는다.

**팬아웃 (병렬 서브에이전트)** — 서로 몰라도 되는 것
예: 비주얼/아트, 사운드, 카피/문구, 독립 UI 컴포넌트, 문서

**순차 (한 에이전트가 처음부터 끝까지)** — 아래 중 **하나라도** 해당하면 순차
- 같은 상태·데이터 구조를 **쓰기(write)** 한다
- 같은 파일을 수정한다
- 실행 순서가 결과를 바꾼다
- 판단이 애매하다 → **순차로 닫는다** (fail-closed)

> 서로를 호출하지 않는다고 독립인 게 아니다. 같은 상태를 만지면 결합돼 있다.
> 이걸 병렬로 쪼개면 부분별로는 그럴싸한데 **이음매에서 반드시 터진다.**
> 코어 로직(상태 머신·충돌 판정·데이터 흐름)은 거의 항상 순차 통이다.

프롬프트에 순차 항목을 적을 때는 **이유까지 같이 적는다.** 이유가 없으면 받는 모델이
효율을 이유로 쪼갠다.

### 4단계 — 검증 체크리스트

**Yes/No로만 답할 수 있는 항목**을 7개 내외로 만든다. 1단계 리서치에서 뽑은 구체적 사실을
그대로 검증 항목으로 바꾸는 게 가장 좋다.

| 나쁜 항목 | 좋은 항목 |
|---|---|
| 애니메이션이 자연스러운가 | 전환 애니메이션이 200ms 이하이고 끊김이 없는가 |
| 원작 느낌이 나는가 | 적이 줄어들수록 이동 속도와 사운드 템포가 실제로 빨라지는가 |
| UI가 예쁜가 | 다크모드에서 모든 텍스트 대비가 4.5:1 이상인가 |

"좋은가"로 끝나는 항목은 전부 다시 쓴다.

### 5단계 — 프롬프트 조립

아래 템플릿을 채운다. 섹션 순서를 바꾸지 않는다.

````markdown
# 목표

{{산출물}}을(를) 만들어줘. **{{기준점}}** 수준이어야 한다.
{{기술 스택 못박기 — 빌드 없이 실행 / 특정 라이브러리 / 단일 파일 등}}

"동작하는 수준"이 아니라 "{{기준점}}과 나란히 놓고 비교해도 밀리지 않는 수준"이 목표다.

## 기준점 상세

{{리서치로 확보한 구체적 사실 — 3~6개 불릿. 수치·화면구성·상징적 특징}}

{{재현 대상이면: 공개 스펙·스크린샷·영상 자료를 직접 조사해서 반영해.}}

## 병렬로 진행할 것 (서브에이전트 팬아웃)

아래 항목은 서로 독립적이다. 각각 별도 서브에이전트에 배분해서 동시에 진행해.

- {{항목 A}}
- {{항목 B}}
- {{항목 C}}

## 순차로 진행할 것 (쪼개지 마)

{{코어 항목}}은 한 에이전트가 처음부터 끝까지 맡아.
이유: {{공유 상태 명시 — 예: 셋 다 같은 엔티티 배열과 프레임 틱을 쓴다}}
여기를 병렬로 쪼개면 부분별로는 그럴싸해 보여도 이음매에서 버그가 난다.

## 검증

만드는 에이전트와 **별개의** 검증 에이전트를 둬. 자기가 만든 걸 자기가 채점하지 마.
검증자는 아주 가혹한 비평가여야 하고, **{{기준점}}의 공개 자료를 직접 조사해서**
나란히 놓고 블라인드로 비교 판정해.

체크리스트 — 전 항목 Yes여야 통과:

- [ ] {{항목 1}}
- [ ] {{항목 2}}
- [ ] {{항목 3}}
- [ ] {{항목 4}}
- [ ] {{항목 5}}
- [ ] {{항목 6}}
- [ ] {{항목 7}}

{{UI 산출물이면: 추가로 디자인 평가와 사용성 테스트를 수행하고 100점 만점으로 채점해.}}

## 종료 조건

체크리스트 전 항목 Yes + 블라인드 비교에서 {{기준점}} 대비 {{N}}점 이상.
미달이면 지적된 항목만 다시 만들어서 재검증해. 최대 {{M}}라운드.
{{M}}라운드까지 통과 못 하면 멈추고, 남은 미달 항목과 그 이유를 보고해.

같은 지적이 3라운드 연속 반복되면 접근 방식이 틀린 것이다. 멈추고 보고해.
````

**마지막 문단(같은 지적 3라운드 반복)을 빼지 않는다.** 루프가 실패로 끝나는 경우보다
같은 자리를 맴돌며 토큰만 태우는 경우가 훨씬 흔하고 훨씬 비싸다.

### 6단계 — 저장 및 실행 안내

파일로 저장한다. `--out`이 없으면 `./prompts/oneshot-{{슬러그}}.md`.

저장 후 아래를 그대로 출력한다:

```
저장: {{경로}}

실행 방법 (별도 디렉토리에서 새 세션 권장):
  cd <작업할 빈 디렉토리>
  git init
  claude

  그다음 프롬프트 창에:
  /loop ultracode
  <저장된 프롬프트 내용 붙여넣기>
```

**작업 디렉토리를 반드시 비워 둘 것을 안내한다.** 이 프롬프트는 5~10시간 돌면서
수십~수백 개 파일을 만든다. 기존 프로젝트 안에서 돌리면 안 된다.

## 품질 자가점검

프롬프트를 내놓기 전에 아래를 확인한다. 하나라도 No면 고쳐서 다시 만든다.

- [ ] 기준점이 실명으로 박혀 있는가 (○○ 앱, ○○ 게임 — "업계 최고" 같은 말 아님)
- [ ] 리서치로 얻은 구체적 사실이 3개 이상 들어갔는가
- [ ] 팬아웃 통과 순차 통이 명시적으로 나뉘어 있는가
- [ ] 순차 항목에 **이유**가 적혀 있는가
- [ ] 검증자 분리 문장이 있는가
- [ ] 체크리스트가 전부 Yes/No로 답 가능한가
- [ ] 종료 조건에 **숫자**(점수·라운드 상한)가 있는가
- [ ] 정체 감지 문단(같은 지적 3라운드)이 있는가

## 하지 말 것

- 리서치 없이 템플릿만 채우기 — 그러면 이 스킬을 쓸 이유가 없다
- 사용자에게 3개 이상 질문하기 — 인터뷰 스킬이 아니다
- 프롬프트를 직접 실행하기 — 이 스킬의 산출물은 텍스트 파일까지다
- 체크리스트에 "잘 동작하는가", "보기 좋은가" 넣기
